# 트러블슈팅: 게이트웨이와 CoreService의 공개 경로 불일치

커밋: `e7b38ab` (2026-06-12)

## 증상

회원가입과 상품 등록 화면에서 카테고리·취미 드롭다운이 **비어 있을 때도 있고 정상일 때도** 있었습니다.

- DB에는 카테고리 20종과 취미 데이터가 있었습니다.
- 쿼리와 프론트엔드 파싱도 정상이었습니다.
- 재현이 일정하지 않아 원인을 찾기 어려웠습니다.

## 원인

브라우저에서 같은 요청을 토큰이 있을 때와 없을 때로 나눠 보내 보았습니다.

```
GET /api/core/hobbies/categories   (토큰 없음)  → 401 "로그인이 필요한 서비스입니다."
GET /api/core/hobbies/categories   (유효 토큰)  → 200, data 20건
```

- CoreService `SecurityConfig`는 이 경로를 `permitAll`로 공개하고 있었습니다.
- 그런데 게이트웨이 `JwtAuthenticationFilter.PUBLIC_PATHS`에는 이 경로가 없었습니다. 그래서 요청이 CoreService에 닿기 전에 게이트웨이에서 401로 끊겼습니다.

"간헐적"으로 보인 이유는 다음과 같습니다.

- 회원가입 화면은 항상 로그아웃 상태라서 늘 비어 있었습니다.
- 상품 등록 화면은 토큰이 만료됐을 때만 비었습니다.

## 해결 방안 비교

| 방안 | 장점 | 단점 |
|---|---|---|
| ① 프론트엔드에 카테고리·취미를 하드코딩 | 네트워크 호출이 없음 | DB와 이중 관리, 데이터를 바꿀 때마다 재배포, 단일 출처 위배 |
| ② 공개 화면용 임시 토큰을 발급해서 호출 | 기존 인증 경로를 재사용 | 공개 참조 데이터에 인증을 끼워 넣는 부자연스러운 구조, 발급 로직 추가 |
| **③ 게이트웨이 공개 경로에 취미 경로를 추가 (채택)** | 1개 파일 2줄 수정, DB 단일 출처 유지, 토큰 만료와 무관하게 동작 | 공개 경로 목록 두 곳을 함께 관리해야 함 |

## 결정

취미·카테고리는 원래 공개 참조 데이터이고, CoreService도 이미 공개로 설계해 두었습니다. 그래서 게이트웨이를 CoreService 정책에 맞추는 ③이 의도에 가장 맞고 변경 범위도 가장 작았습니다.

```java
// GateWay JwtAuthenticationFilter.PUBLIC_PATHS
"/api/core/hobbies",
"/api/core/hobbies/**",   // CoreService SecurityConfig와 동일하게 공개
```

## 검증

- 토큰 없이 두 엔드포인트가 200을 반환하는지 확인했습니다.
- 로그아웃 상태의 회원가입 화면에서 드롭다운이 정상으로 표시되었습니다.
- 보호 경로(상품 등록)는 여전히 401을 반환해, 보안 회귀가 없음을 확인했습니다.

## 배운 점

- 게이트웨이와 서비스가 각각 인가를 하는 구조에서는 공개 경로 목록이 쉽게 어긋납니다.
- "DB와 서비스는 정상인데 화면만 빈다"면 **가장 바깥 계층(게이트웨이)의 인가부터** 의심해야 합니다.
